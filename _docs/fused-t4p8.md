## 1. What was built, and why it is the same experiment

### 1.1 The generator

`_docs/fused-t4p8/gen_set.py` **imports** `_docs/fused-truncation/gen_trunc.py`
(and through it `fused-small-path/gen.py`) and reuses `tree()` and `body()`
verbatim; nothing is copied. It generalises the cutoff `C` to an arbitrary,
possibly discontiguous **body set**. The shipped per-`n` schedule is unchanged:
`k = (0.45, 0.30, 0.45, 0.30, 0.45, 0.45, 0.45, 0.70)`.

The self-check that makes this a controlled extension, run on **all four hosts**:

```
  {1..4}: t4=c3f72ffe4679c67064f5439a1d97c712 g4=c3f72ffe4679c67064f5439a1d97c712  SAME
  {1..5}: t5=8fd4eb045fc05dc8138eeb4f48a6f57b g5=8fd4eb045fc05dc8138eeb4f48a6f57b  SAME
  {1..7}: t7=575eddac98ea8e2fedc8fd7bd594cf04 g7=575eddac98ea8e2fedc8fd7bd594cf04  SAME
  {1..8}: t8=6578449791d0522b4fe474e2b0950302 g8=6578449791d0522b4fe474e2b0950302  SAME
```

i.e. on a contiguous set `gen_set.py` reproduces `gen_trunc.py`'s object
**bit for bit**, and `t8`'s md5 is still the `tuned.o` md5 measured as variant C
in `fused-small-path-experiment.md`. Every object in this run is md5-identical
across r8g, GV3, GV4 and GV5 (same gcc 13.3 / binutils 2.42), so the static
checks are literally the same objects on every core.

### 1.2 The dispatch — the one genuinely new piece of code

A contiguous cutoff needs one test. `{1,2,3,4,8}` needs two, and the ordering is
a real design choice, so both were built and measured:

**`t4p8` (design A, "small first")** — shipped:

```
	cmp	x9, #64				//[FUSE] nblk <= 4 ?
	b.le	.L256_dec_fused_small
	cmp	x9, #128			//[FUSE] nblk == 8 ?
	b.eq	.L256_dec_fused_8
```

**`t4p8b` (design B, "big first")** — keeps the `nblk > 8` bulk path at exactly
the two instructions every contiguous truncation pays, at the price of a *taken*
branch:

```
	cmp	x9, #128			//[FUSE] nblk > 8: not fused
	b.gt	.L256_dec_nofuse
	b.eq	.L256_dec_fused_8
	cmp	x9, #64				//[FUSE] nblk <= 4 ?
	b.le	.L256_dec_fused_small
.L256_dec_nofuse:
```

Everything else is unchanged: the region is appended at `.L256_dec_ret`, the
compare tree over `{1,2,3,4}` is the tree `t4` uses, and bodies 1–4 and 8 are the
bodies `t8` ships.

`.text`: `t4p8` **8832** (×1.7778), `t4p8b` **8836**. Growth accounting matches
the published per-body costs exactly: 4968 + (bodies 1,2 + tree) 832 + body3 672
+ body4 840 + body8 1520 + 8 (second test) = 8840 − 8 (one fewer tree level than
`t8`) → 8832.

## 3. Fixed-length measurement

Discipline as established: every variant `objcopy --redefine-sym`'d to a distinct
symbol and linked into **one** 12-slot binary, round-robin with the slot order
rotated every rep, `taskset -c 3`, 200-call warm-up per pass, best of 300 reps.
`base` is pinned to link slot 0 as in the truncation run so the tables are
comparable; the other 11 slots are permuted over **6 link orderings / 30
processes on r8g** and **3 orderings / 15 processes** on each GV host. Slots
`baseAA`, `baseAB` are the baseline object again (A/A floor twice), `dsp0AA` is
the dispatch control again, `t4p8AA` is `t4p8` again — so the variant under test
has its own placement floor.

### 4.3 The traffic-ratio scan and the measured break-even

Mixes R1…R6 contain **only** 80 B and 128 B calls in a fixed ratio, so they read
the decision directly. Δ % vs HEAD, median of 9 processes:

| ratio 128 B : 80 B | r8g `t5` / `t4p8` | GV3 V1 | GV4 V2 | GV5 V3 |
|---|---:|---:|---:|---:|
| 1:1 | −16.15 / −4.77 | −14.00 / **+1.18** | −16.18 / −4.82 | −13.31 / **+0.83** |
| 2:1 | −11.75 / −6.05 | −8.72 / −4.14 | −11.78 / −6.08 | −8.62 / −0.90 |
| 3:1 | −9.01 / −6.76 | −7.76 / −4.81 | −9.10 / −6.80 | −6.60 / −2.42 |
| 4:1 | −7.45 / −7.26 | −6.46 / −5.63 | −7.44 / −7.24 | −5.35 / −3.25 |
| 6:1 | −4.73 / **−8.19** | −4.44 / **−6.97** | −4.81 / **−8.29** | −3.36 / **−5.05** |
| **interpolated break-even** | **4.10 : 1** | **4.49 : 1** | **4.11 : 1** | **5.11 : 1** |

Two things fall out.

1. **The measured break-even is worse for `t4p8` than the fixed-length estimate
   on every core** (4.10 vs 3.73 on V2, 4.49 vs 3.65 on V1, 5.11 vs 4.32 on V3),
   because mixing costs body 8 more of its gain than it costs body 5 of hers.
2. **Body 8's gain is fragile under mixing.** At 1:1, half the calls are 128 B,
   so the fixed-length −10 % predicts about −5 % overall; `t4p8` delivers
   **−4.8 % on V2 but +1.2 / +0.8 % — nothing at all — on V1 / V3**. `t5` in the
   same stream delivers −16.2 / −14.0 / −13.3 % against a −18 % prediction, i.e.
   it keeps ~74–90 % of its fixed-length value.

That is the answer to the mechanism question in its sharpest form: **the "code
actually touched" tax does not disappear when the middle bodies are removed — it
relocates from a throughput penalty on the other lengths to a near-total loss of
body 8's own benefit whenever 128 B calls are interleaved with anything else.**
The 8th body is the marginal case in the fixed-length curve (1.3 of 34.0 points)
and it is the fragile one under mixing, on three microarchitectures.

## 5. Verdict

1. **The prediction is confirmed. `t5` dominates `t4p8`.** Same 5 proved paths;
   `t5` is 508 B smaller (8324 vs 8832), returns 3.4–3.9 more points of
   uniform-small-traffic value on every core, and is equal or better in mixes A,
   B, C and D on every core. `t4p8` is better only in traffic deliberately
   weighted to 128 B.
2. **The break-even 128 B : 80 B traffic ratio is ~4 : 1, not 3.5 : 1** — 4.10:1
   (V2, two instances), 4.49:1 (V1), 5.11:1 (V3) measured in an interleaved
   80/128 stream; 3.65–4.32:1 from fixed-length savings alone. A workload would
   need **more than four 128-byte records for every 80-byte record** before
   `t4p8` is preferable to `t5`, and on V3 more than five. If such a workload
   existed, `t8` (or `t7` + the exact-8 drain) would beat both anyway.
3. **Body 8's mixing penalty does not require the middle bodies.** It survives as
   a 0.5–0.9 % throughput cost in mixes A/B on V1 and V2 (paired, both address
   ranks; tie on V3), *and* — more decisively — as the near-total loss of body
   8's own 128 B gain when 128 B calls are interleaved with 80 B calls on V1 and
   V3. The prior single-core attribution ("what costs is the amount of code
   actually touched") stands, and `t8`-vs-`t7` now reproduces on **all three**
   microarchitectures.
4. **Nothing else regresses.** Fall-through lengths, 256 B and 4 KB are
   unaffected within the A/A floor on all four cores, even with 4 dispatch
   instructions instead of 2; frame stays 80 B; the not-fused path is
   instruction-for-instruction HEAD's.
5. **Recommendation: do not build `t4p8`.** A measured negative: the
   discontiguous set buys nothing that the contiguous `t5` does not buy more
   cheaply, and the family's recommendation (`C = 7` for value, `C = 5` if proof
   cost dominates) is unchanged.

## 6. What still rests on one core

The cross-core extension covers the two things that mattered. Remaining
single-host items:

* **The make-driven KAT** (real `arm/Makefile` + `arm/aes-gcm/kat/Makefile`, with
  the make-built object byte-compared to the harness object) ran **only on
  r8g**, because the GV hosts have no checkout of the tree. This is not a
  microarchitectural claim, and every object is md5-identical on all four hosts,
  so the risk is nil.
* **The 6-ordering / 30-process precision** of Table 1 exists only for r8g; the
  GV hosts got 3 orderings / 15 processes. GV4 reproduces r8g to ≤ 0.2 points at
  every length, so this affects resolution, not sign.
* **Mix A on the two V2 hosts is noise-limited this run** (`t4p8` A/A spread
  5.2–5.9 %); the mix A conclusions are carried by the V1/V3 paired controls and
  by the B/C/F/R mixes. A rerun with more processes would tighten it but cannot
  change the direction, which is consistent on V1 and V3.
* All numbers are single-thread, `taskset`-pinned, and say nothing about SMT or
  multi-tenant instruction-cache pressure — where a 508 B/3544 B code-size
  difference would, if anything, favour the *smaller* variant, i.e. `t5` again.
