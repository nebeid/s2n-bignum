Our branch [`aes-gcm-nblock-tail`](https://github.com/nebeid/s2n-bignum/tree/aes-gcm-nblock-tail) is proving the same GCM-encrypt tail bands as your [`aes256_gcm_tail`](https://github.com/manastasova/s2n-bignum-dev/blob/004b1a06f621c514f73a37a303b9e1bd10d0827b/arm/proofs/aes256_gcm.ml) — your [`AES256_GCM_ENCRYPT_LT_2BLOCK_CONCRETE`](https://github.com/manastasova/s2n-bignum-dev/blob/004b1a06f621c514f73a37a303b9e1bd10d0827b/arm/proofs/aes256_gcm.ml#L1589) = our [`AESV8_GCM_8X_ENC_256_LE2BLOCK`](https://github.com/nebeid/s2n-bignum/blob/bb2e2585d1ad80375fd06b09251bc52149ebef9e/arm/proofs/aesv8_gcm_8x_enc_256_le2block.ml#L132), and you're ahead — so let's converge. Four items:

**1. AES primitive (D2) — proposing you adopt ours: let's both target the existing shared `aes256_encrypt`.** Proposal: standardize the GCM block primitive on [`aes256_encrypt`](https://github.com/nebeid/s2n-bignum/blob/bb2e2585d1ad80375fd06b09251bc52149ebef9e/arm/proofs/utils/aes_encrypt_spec.ml#L63) (int128-list keys, `aes256_encrypt_round` fold) and retire [`aes256_block_enc`](https://github.com/manastasova/s2n-bignum-dev/blob/004b1a06f621c514f73a37a303b9e1bd10d0827b/arm/proofs/utils/aes256_gcm_block_enc_spec.ml#L18). `aes256_encrypt` is already the shared AES-256 block spec — XTS builds on it and so do all our GCM bands; it lives in `arm/proofs/utils/aes_encrypt_spec.ml` (needs only `common/aes.ml`, so it can move to `common/` if you'd prefer). The two compute the same AES-256, differing only in where each round key is added, and **no bridge is needed**: the postcond's `aes256_encrypt` unfolds to the `aese`/`aesmc` instruction tower in one rewrite (`REWRITE_TAC[aes256_encrypt_round; aese; aesmc]`, let-reduce) — our bands never mention `aes256_block_enc`. For your existing theorems already stated in `aes256_block_enc`, you can either re-close them against `aes256_encrypt` directly, or — if you'd rather not touch the proof bodies — use the optional adapter we've proven, [`AES256_BLOCK_ENC_EQ_ENCRYPT`](https://github.com/nebeid/s2n-bignum/blob/bb2e2585d1ad80375fd06b09251bc52149ebef9e/arm/proofs/utils/aes256_block_enc_eq_encrypt.ml#L54) (`aes256_block_enc input k0..k14 = aes256_encrypt input [k0;...;k14]`, one rewrite per use, no cheats), which is throwaway once migration is done. Either way GCM and XTS end on one block primitive.

**2. Stack frame / entry (D10) — proposing you adopt ours: the saves-first prologue reorder.** We reorder the `.S` prologue so all four callee-saves (`stp d8..d15`) come first and the arg-setup follows ([our `aesv8_gcm_8x_enc_256.S`](https://github.com/nebeid/s2n-bignum/blob/bb2e2585d1ad80375fd06b09251bc52149ebef9e/arm/aes-gcm/aesv8_gcm_8x_enc_256.S#L30) lines 30–33 contiguous, vs your interleaved [`aes256_gcm.S`](https://github.com/manastasova/s2n-bignum-dev/blob/004b1a06f621c514f73a37a303b9e1bd10d0827b/arm/aes-gcm/aes256_gcm.S#L36) where `lsr/mov` sit between the `stp`s); this keeps the C args in `X0..X6` at the first body instruction, so `C_ARGUMENTS` holds when we enter the body at pc+0x18 (e.g. [`AESV8_GCM_8X_ENC_256_LE2BLOCK`](https://github.com/nebeid/s2n-bignum/blob/bb2e2585d1ad80375fd06b09251bc52149ebef9e/arm/proofs/aesv8_gcm_8x_enc_256_le2block.ml#L132) runs pc+0x18→pc+0x11d8). It's functionally a no-op — only the prologue offsets change, the **body bytes are byte-identical** and total size is unchanged — but it lets the band theorems state a clean `C_ARGUMENTS` body core. We'd then wrap that core with `ARM_ADD_RETURN_STACK_TAC` to prove the prologue/epilogue and produce a whole-function `..._SUBROUTINE_CORRECT` theorem at pc+0, exactly the XTS pattern ([`AES_XTS_ENCRYPT_SUBROUTINE_CORRECT`](https://github.com/nebeid/s2n-bignum/blob/bb2e2585d1ad80375fd06b09251bc52149ebef9e/arm/proofs/aes_xts_encrypt.ml#L5563)). Since this touches the shipped `.S`, it'd need to land in s2n-bignum and re-import to aws-lc — proposing it as the shared convention so both our band cores and your whole-function theorems sit on one source.

**3. GHASH closure (D7) — we'll adopt yours: it wins on timing.** We timed both ways to discharge the `read Q19` pre-reduction tower: yours — [`ghash_Nblock_karatsuba`](https://github.com/manastasova/s2n-bignum-dev/blob/004b1a06f621c514f73a37a303b9e1bd10d0827b/arm/proofs/utils/gcm_aesgcm_nblock_helpers.ml#L192) + the one inductive bridge [`GHASH_NBLOCK_KARATSUBA_EQ_PROP3`](https://github.com/manastasova/s2n-bignum-dev/blob/004b1a06f621c514f73a37a303b9e1bd10d0827b/arm/proofs/utils/gcm_aesgcm_nblock_helpers.ml#L450); ours — crunching the raw tower per band (`MERGE_2BLK`/`FINISH_2BLK`):

| route | N=2 | N=3 | N=4 |

Yours scales flat (~+25 ms/block; hard induction proven once); ours re-runs per band and is brittle. We'll adopt it for our 3..8 ladder and decrypt. (Considered a hybrid — moot: your EQ_PROP3 leaves zero residual operand equalities, since the per-block pack identity is baked into `KARATSUBA_BLOCK_PACKS_TO_PMUL_CLEAN`.)
